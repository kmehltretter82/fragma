Subject: module: reject out-of-range relocation target indices

Affected versions

The observed ARM32 path was introduced by commit 7d485f647c1f ("ARM:
8220/1: allow modules outside of bl range"). The observed PA-RISC path was
introduced by commit c298be74492b ("parisc: fix module loading failure of
large kernel modules"). The bug remains present at upstream commit
28924df2a08f440c73991b83028032c901de2ae4 dated 2026-09-07.

Problem

The generic module loader validates ELF section contents and names before it
calls module_frob_arch_sections(), but does not validate the sh_info target
index of SHT_REL or SHT_RELA sections. ARM32's ARM_MODULE_PLTS hook forms
sechdrs + sh_info and reads the resulting section header. An out-of-range
index therefore forms an invalid pointer and can cause a kernel paging fault.
The later apply_relocations() code skips invalid indices, but runs too late to
protect the architecture hook.

PA-RISC uses the same unchecked value to index an e_shnum-sized heap array.
The source reads and later updates stub_entries at that index. A separate
same-input QEMU A/B faults on the out-of-bounds read before the fix. The later
store was not reached by that witness.

Reproducer status

A source reproducer is available but is not included in the public project.
It builds a normal ARM32 module and changes only the first SHT_REL section's
sh_info from 10 to 0x10000000. On QEMU virt/TCG, the control module loads and
unloads. The malformed module faults in
module_frob_arch_sections()+0x160/0x2b8 on the original kernel. With the
proposed fix, the same module is rejected with ENOEXEC and init continues.

The PA-RISC reproducer changes only the four-byte, big-endian sh_info field of
a SHT_RELA section which contains a counted R_PARISC_PCREL17F relocation. The
control module loads and unloads on both kernels. The malformed module causes
a Data TLB miss at module_frob_arch_sections()+0x11c before the fix. After the
fix it returns ENOEXEC, prints the invalid index and reaches the guest
completion marker.

Triggering conditions

The demonstrated path uses a 32-bit ARM kernel with MODULES and
ARM_MODULE_PLTS enabled, CAP_SYS_MODULE, and a module-signature policy that
permits the test module. VMSPLIT_2G was enabled in the tested multi_v7
configuration; it is a test detail, not claimed as a necessary condition.
Because loading a malformed module already requires module-loading privilege,
this is classified as a regular kernel robustness bug, not a security
vulnerability.

Proposed fix and verification

Validate relocation section target indices in elf_validity_cache_sechdrs()
before any architecture hook can consume them. The QEMU test was run A/B at
commit b9b3e33b70b71e516930117e21de3ad2a7723747 with GCC 15.2.0 and QEMU
10.2.1. The full patched ARM32 zImage also builds without warnings at current
base commit 28924df2a08f440c73991b83028032c901de2ae4. The patch applies cleanly
there, git am succeeds in a fresh worktree, and strict checkpatch reports no
issue. The named submitter explicitly requested the included Signed-off-by
trailer.

Testing gaps

The exact QEMU A/B was not repeated at the newer base because the relevant
architecture function and loader ordering are unchanged; a full current-base
ARM32 build was completed instead. The installed sparse 0.6.4 is too old for
the current kernel build's sparse gate, so no sparse result is claimed. No
hardware run was performed. ARM64, RISC-V and LoongArch completed full patched
vmlinux builds after a source audit found the same early indexing pattern in
their hooks. They were not runtime A/B tested.
